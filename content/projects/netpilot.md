## Overview

NetPilot is a small backend service that exposes infrastructure *inspection* tools in the shape used by the Model Context Protocol (MCP). The tools are things an assistant would reasonably want to call, such as "list the degraded nodes at this site" or "has this node's config drifted from its baseline?" The service is built so that every one of those calls is bounded, typed and recorded.

It is a personal portfolio project, and everything it touches is simulated. The network inventory, devices and configuration drift are all generated by a seed script, and no real infrastructure is involved.

## Problem

Engineers who run infrastructure want to ask an assistant questions like *"which devices have config drift?"* The risk is that the easiest way to make that work is to give the model broad access and hope it behaves. That leaves no clear line between looking at something and changing it, and no reliable record of what the AI layer actually did.

## Why it matters

As teams wire language models into operational tooling, the permission model matters more than the prompt. A tool layer that makes the safe path the default can be reviewed, tested and audited like any other service. NetPilot demonstrates that pattern at a small scale:

- Every tool declares the minimum scope it needs: `read`, `plan` or `mutate`.
- A call is rejected before it touches data if the caller's token doesn't hold that scope.
- Every call, successful or not, produces exactly one structured audit record.

## My role

This is a solo project. I designed the architecture and wrote the service, the simulated network, the tests and the CI pipeline.

## Technical approach

**A transport-agnostic tool registry.** Each tool is a plain Python function plus a Pydantic model for its arguments. The registry stores a `ToolSpec` with the tool's name, description, required scope, argument model and handler. The argument model does two jobs: it validates input, and it generates the JSON schema advertised to clients.

```python title="mcp_server/tools/base.py (excerpt)"
@dataclass(frozen=True)
class ToolSpec:
    name: str
    description: str
    required_scope: Scope
    args_model: type[BaseModel]
    handler: Callable[..., Any]

    def input_schema(self) -> dict:
        return self.args_model.model_json_schema()
```

Handlers never deal with HTTP. They receive a caller context and typed arguments, so serving the same tools over a real MCP transport later means changing the entry point rather than the tool logic.

**Permission boundaries as the first line of every tool.** Each handler calls `require_scope(ctx, REQUIRED_SCOPE)` before doing anything else. Scopes run from `read`, which inspects state, to `plan`, which computes a proposed change without applying it, to `mutate`, which applies a change. No tool uses `mutate` yet. The scope exists from day one so the permission model doesn't have to change shape when the first mutating tool arrives.

**Audit logging that can't be skipped.** `audit_call` is a context manager, so the record is written in a `finally` block whether the tool succeeds or raises. Each line holds the tool, the required scope, the arguments, the status, a short result summary, any error and the duration. That means you can answer *"what did the AI layer actually call?"* from the log alone, independently of any chat history.

**Careful error mapping.** An unknown tool returns `404`, a missing scope `403`, invalid arguments or an unknown node `422`, and a missing or wrong token a generic `401`. The `401` deliberately doesn't say whether the token was unknown or wrong. That distinction lives in the audit log, not in the response.

## Architecture

The diagram above shows the request path. Two tools exist today:

| Tool | Scope | What it does |
| --- | --- | --- |
| `network_inventory` | `read` | Lists simulated nodes, filterable by site and status |
| `config_validate` | `read` | Compares a node's current config with its recorded baseline and reports drift |

The seed script creates 15 nodes across three simulated sites. It then deliberately drifts three of them: a rolled-back firmware version, a weakened TLS minimum version and debug logging left on. This gives the drift check something real to find.

## Technology choices

- **FastAPI and Pydantic v2.** Typed request handling, and JSON schemas generated from the same models used for validation.
- **SQLAlchemy 2.0, with SQLite by default.** The project runs with zero setup, and Postgres is one environment variable away through Docker Compose.
- **pytest and Ruff in GitHub Actions.** Lint runs first, then the test suite, on every push and pull request.

## Testing and reliability

The test suite exercises the API end to end against seeded data. It covers authentication failures, tool listing, filtering by site and status, detection of a known drift case, a clean node reporting no drift, and the `422` and `404` paths. There are 10 tests, and they pass when run locally.

## Results and limitations

NetPilot is at the end of its first milestone. Everything is read-only, and the tools are served over plain HTTP using MCP-style naming rather than the MCP protocol itself. Authentication uses a single configured token with a fixed set of scopes. That suits a demonstration, but it is not a production identity model.

## What's next

The roadmap in the repository covers a Kubernetes inspection tool and Terraform plan analysis (against `kind` and LocalStack), and then a single mutating remediation tool. Holding the `mutate` scope alone won't be enough to use it, because it will also require a separate human-approval step. After that come CI/CD improvements and metrics.
